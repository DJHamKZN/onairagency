# Экспорт, резервные копии и восстановление

## Что есть в прототипе

| Что | Как | Кто | Содержимое |
|---|---|---|---|
| Резервная копия | «Данные и настройки → Скачать резервную копию» или `GET /api/admin/backup` | владелец | всё, кроме паролей и сессий: компании, контакты, возможности (с версиями записей), журнал, снимки, настройки. Поле `warning` — «ВНУТРЕННЯЯ РЕЗЕРВНАЯ КОПИЯ… не передавать клиенту» |
| Клиентский экспорт | вкладки «КП и версии» и «Диагностика» | владелец, PM (аудит — и ведущий) | только разрешённые поля; генерация пишется в журнал |
| Внутренний документ | «3. Внутренний Word команды» | владелец (PM — с разрешением) | экономика, задачи, все находки |

Это **ручной** экспорт. Автоматического резервного копирования нет.

## Восстановление на чистой базе (проверено)

```bash
cd crm-prototype
npm run restore-check -- путь/к/onair-crm-backup-….json          # проверить и удалить проверочную базу
npm run restore-check -- путь/к/копии.json --keep                  # оставить проверочную базу в data/
```

Шаги `restore-check`: размер ≤ 10 МБ → разбор JSON → `format` и `schemaVersion` 1 или 2 (копия версии 1 приводится к схеме 2: чек-лист запуска, см. DATA_MODEL) → типы (zod) → ссылки
(компании, пользователи, источники, находки, работы, расчёты, версии КП, снимки, связанные возможности, дубликаты ID) →
загрузка в **новый** файл `data/restore-check-<время>.sqlite` → повторный экспорт и сверка количества возможностей, компаний,
событий, снимков, версий КП и версий записей. Рабочая база не открывается.

Через интерфейс: выбрать файл → предпросмотр (база не меняется, показаны ошибки или количества) → ввести «ЗАМЕНИТЬ БАЗУ» →
восстановление в отдельный файл, сверка, замена; прежний файл остаётся как `crm.sqlite.before-import-<время>`.
Пароли пользователей переносятся с текущего сервера по ID пользователя (в копии их нет).

Ручное восстановление «с нуля»: остановить сервер → переименовать `data/crm.sqlite` → запустить сервер на пустой базе
→ войти владельцем → импортировать копию. Учтите: при пустой базе сервер сначала загрузит демо-данные; импорт их заменит.

## Перед реальными данными и многопользовательской работой (обязательно, и доказать тестами)

1. Серверная развёртка с HTTPS, закрытым доступом и ответственным за эксплуатацию; решение о хостинге — отдельно.
2. Промышленная БД (например, PostgreSQL) с FK для ключевых сущностей, миграциями и откатом.
3. Аутентификация организации (SSO/2FA), управление пользователями, отзыв сессий, журнал входов.
4. Права на каждом API-действии — сохранить и расширить существующие тесты; тесты на подмену ID для всех маршрутов.
5. Optimistic concurrency на уровне разделов, чтобы снизить конфликты; UX слияния.
6. Защищённый журнал (подпись/внешнее хранилище), политика хранения.
7. Автоматические зашифрованные резервные копии вне машины, регулярная **проверенная** процедура восстановления.
8. Валидация всех payload по схемам; лимиты размера; защита от перебора.
9. Безопасная обработка вложений (хранилище, антивирус, типы), если оригиналы будут храниться.
10. Контроль экспортов: журнал, водяные знаки, запрет внутренних полей — сохранить allowlist-тесты.
11. Ноль секретов во frontend и в репозитории; секреты интеграций — только в серверном хранилище секретов.
12. Политика персональных данных и согласия на запись созвонов — до подключения транскрибации.
